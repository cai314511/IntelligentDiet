## 第一部分：现有界面评估与高校主题方案

### 1. 原始需求

> 审视我当前的系统界面 ui，我想做出每个高校有各自的定制皮肤，即主题背景样式。用户登录绑定高校后，即刻实现对应高校的特定文创，页面、按钮样式都为该高校定制化皮肤。这该怎么实现？参考目前市面上具有近似功能的 app 产品和主流做法告诉我。先向我对齐，不随意更改系统代码，仅告诉我该如何实现。

### 2. 推荐方向与检查范围

可以实现，而且当前系统已经有可复用的换肤基础。推荐采用 **“一套网站＋高校主题包＋账号绑定后自动应用”** 的方案。每所学校有自己的视觉风格，同时共用点餐、订单、营养师等功能。

此前已核对线上站点和本地前端代码：主要脚本及主题文件一致。该轮只做源码和页面结构审视，没有修改文件，也没有进行逐像素视觉验收。

网站预览：[智饷高校智慧食堂](https://zhixiangcanteen.netlify.app/)。

### 3. 对当前界面的判断

C 端以蓝白色、毛玻璃导航、圆角卡片为基础，已经有“极简、动漫、电竞、国风、音乐、运动”六套主题。[现有主题样式](<C:/Users/蔡雨轩/Desktop/ai project/zhixiang/canteen/themes.css>)能够统一调整主色、背景、文字颜色和部分圆角。

距离高校定制，主要还有四处差距：

- **主题没有绑定学校。** 当前只把选中的主题保存在浏览器中；登录接口和用户表定义还没有学校字段，也就无法跨设备跟随账号。
- **换肤覆盖不完整。** 一些渐变、灰色背景、按钮状态和圆角仍写在页面里，可能出现主体换色、局部仍保留原样的情况。
- **校园特色集中在个别文案。** 例如文创页面直接写着“CUFE · 春季嘉年华”，还没有统一的学校标识、地标插画和文创素材配置。
- **视觉主题与推荐逻辑混在一起。** [主题脚本](<C:/Users/蔡雨轩/Desktop/ai project/zhixiang/canteen/themes.js>)会根据电竞、运动等皮肤改变菜品排序。高校皮肤应控制外观，营养推荐应由健康资料、饮食偏好和菜单决定，建议拆开。

另外，当前点餐页把“风格宇宙”和主题推荐放在餐厅信息之前。学校主题自动生效后，建议将换肤入口移到“我的 → 校园装扮”，首页优先展示校园身份、食堂状态和点餐入口。

### 4. 可以借鉴的产品与主流做法

以下产品分别提供了所需能力的一部分，并非都具备“高校绑定自动换肤”这一完整功能。

| 参考对象 | 已有做法 | 智饷适合借鉴的部分 |
| --- | --- | --- |
| [QQ 个性装扮](https://vip.qq.com/) | 以主题和装扮形成个性化视觉体验 | 高校皮肤应是一套协调的背景、图标、卡片和装饰素材，而不只是一张壁纸 |
| [Slack 工作区主题](https://slack.com/help/articles/205166337-Change-your-Slack-theme) | 可为不同工作区设置不同主题，主题跟随用户跨设备使用 | 根据当前学校切换视觉，同时保存用户偏好 |
| [Microsoft Entra 组织品牌](https://learn.microsoft.com/en-us/entra/fundamentals/how-to-customize-branding) | 组织可配置登录背景、标志、页眉等品牌元素 | 学校维护统一品牌配置，绑定该学校的用户获得对应体验；这里只借鉴机制，无需购买其服务 |

技术上可以参考 [Ant Design 的主题机制](https://ant.design/docs/react/customize-theme-cn)：把颜色、圆角、边框和组件样式集中配置，通过主题统一切换。**项目用现有 JavaScript 和 CSS 变量就能实现，不必为换肤迁移框架。**

### 5. 高校皮肤的设计组成

每套皮肤由三部分组成：

1. **基础视觉参数。** 学校主色、辅助色、页面底色、文字色、卡片边框、阴影，以及按钮的默认、悬停、按下、禁用和键盘焦点状态。
2. **校园文创素材。** 学校标识、代表建筑插画、校园纹样、小智校园装扮、空状态插画，以及校庆等活动素材。
3. **组件外观配置。** 按钮采用胶囊形还是较方正的圆角，卡片采用描边还是柔和阴影，栏目标题采用哪种装饰。

页面布局和操作位置保持统一，视觉气质可以明显不同。例如，以中央财经大学为首个试点，在核实学校视觉规范和素材使用权限后，可以让：

- 顶栏显示“智饷 · 中央财经大学”和校区。
- 首页顶部使用校园地标插画。
- 页面背景铺低对比度校园纹样。
- 按钮、选中标签、购物车和导航采用统一校园色。
- 小智使用校园配饰，文创页展示本校活动和作品。

文创表达可以在首页、文创页、个人中心更丰富；菜单、结算和营养信息应保留清晰的文字与背景对比。错误、售罄、支付状态等提示仍保留明确含义，不随校色任意改变。

B 端建议采用相同学校标识和主色，但减少背景插画，保证表格和管理操作易读。

### 6. 登录后自动换肤的流程

```text
用户登录
   ↓
服务器返回账号绑定的学校
   ↓
读取该学校已发布的主题配置
   ↓
同步应用颜色、按钮、卡片和校园素材
   ↓
缓存主题，下次打开时优先显示
```

第一次登录且没有绑定学校时，先选择学校和校区；已有绑定的用户直接进入对应校园。

这里要区分“选择学校”和“通过学校身份验证”：没有学校统一认证接口，仍然可以提供选校绑定和自动换肤，但不能把自行选择学校标成“已认证”。如果以后要控制校内权益，再接入经学校认可的邮箱验证、邀请或人工审核流程。

为了做到“即刻”，建议：

- 登录响应同时携带学校编号和主题版本，减少额外等待。
- 先应用颜色和组件样式，再加载较大的插画。
- 缓存按账号、学校和主题版本区分，避免换账号后沿用上一人的学校。
- 主题加载失败时显示默认主题，保证点餐仍能操作。
- 用户可选择“跟随学校”或“简洁模式”，默认跟随学校。

学校皮肤只决定显示效果。如果未来菜单、订单、活动也按学校区分，服务器还必须按学校限制数据访问，不能依靠前端换肤或学校编号完成权限控制。

### 7. 适合当前项目的落地顺序

1. **先做视觉样板。** 设计默认主题和中央财经大学主题，覆盖首页、菜单、营养师、文创、购物车、登录及个人中心。先确认校园特色的表达程度。
2. **完善现有主题基础。** 扩展 `themes.js`、`themes.css`，统一硬编码样式，拆开皮肤与推荐逻辑，补齐校园素材位置。
3. **接通账号绑定。** 后端增加学校、校区、主题关联；登录返回学校信息，前端自动应用并缓存。
4. **用第二所学校验证复用。** 应当主要增加配置与素材，就能形成明显不同的校园风格。
5. **再考虑后勤配置页面。** 初期用配置文件维护即可；学校增多后，再提供上传素材、预览、发布和恢复上一版的管理入口。

一个实际前提：此前核查的线上版本中，[接口地址](<C:/Users/蔡雨轩/Desktop/ai project/zhixiang/canteen/api.js>)仍指向 `http://localhost:5000/api`，也就是访问者自己的电脑。纯前端可以先演示选校换肤，但真实的“登录绑定、跨设备自动恢复”需要可公网访问的账号后端。这是后续实施的依赖，该轮没有处理它。

建议对齐为：**默认跟随绑定高校，全站组件统一换肤，重点页面展示校园文创，保留简洁模式，首批完成中财主题和默认主题。** 换肤本身不需要付费接口或大模型，后续每接入一所学校，主要增加设计素材和配置即可。

## 第二部分：设计素材、主题配置与 Codex 协作教程

### 1. 原始需求

> 设计素材和配置如何制作？详细教我如何与 Codex 配合做出一整套高校定制个性化皮肤、按键等。

### 2. 协作分工与总体流程

可以把 Codex 当成“能写代码的设计搭档”：**你负责提供校园特色和判断审美，Codex 负责把它整理成设计规范、素材、主题配置和可点击的页面。**

对“智饷”，建议先完整做出中央财经大学的一套主题，再用第二所学校验证是否能复用。该轮只讲做法，没有创建或修改文件。

整个过程按以下顺序推进：

```text
校园资料
   ↓
两个设计方向
   ↓
确认一个方向
   ↓
素材与组件样板
   ↓
页面接入
   ↓
登录自动换肤
```

下面三个阶段的指令，可以依次复制给 Codex；每阶段看过结果再进入下一阶段。

### 3. 第一阶段：提供参考，确定设计方向

不需要先学设计软件，也不需要自己填写颜色代码。先准备这些内容：

| 你提供的资料 | 建议数量 | Codex 如何使用 |
| --- | --- | --- |
| 校徽、学校视觉规范或官网资料 | 1 套 | 确认学校标识和官方配色 |
| 有代表性的校园照片 | 3～5 张 | 提炼建筑轮廓、景观和校园特色 |
| 你喜欢的界面截图 | 2～3 张 | 参考留白、卡片、按钮和整体气质 |
| 你不喜欢的界面截图 | 1～2 张，可选 | 排除不合适的视觉方向 |
| 校园文化关键词 | 3～5 个 | 约束插画、装饰和文案的表达 |
| 当前网站截图 | 首页和一个功能页 | 确认哪些布局需要保留 |

截图可以直接作为附件提供，也可以放进项目文件夹后告诉 Codex 位置。给多张图片时，应说明各自用途，例如：

> 第一张参考建筑外形，第二张参考插画风格，第三张只参考按钮和留白。

学校照片应注明具体校区。这样可以避免把沙河校区和学院南路校区的建筑混成一个不准确的场景。校徽优先使用学校提供的原始文件，校园色也以正式资料为准；没有资料时，先标注为设计提案。

>

> 3. 按钮、卡片、输入框、导航的外观。
> 4. 首页、点餐页和文创页各自呈现什么特色。

### 4. 第二阶段：制作整套素材和组件

#### 4.1 区分视觉素材与界面组件

校园插画、人物形象、背景纹样属于视觉素材；按钮、输入框、菜单卡片属于界面组件。按钮要用代码制作，文字可修改、尺寸可适配，点击和禁用状态也能正常工作。

首套高校皮肤，建议交付以下内容：

| 交付物 | 建议制作方式 | 首版需要什么 |
| --- | --- | --- |
| 学校标识 | 使用已有 SVG 或透明 PNG | 深浅背景下均能清晰显示 |
| 首页校园插画 | 根据校园照片绘制 SVG，或使用图像生成 | 电脑、手机两种构图 |
| 页面背景纹样 | 可平铺 SVG 或 CSS | 低对比度、不干扰阅读 |
| 小智校园装扮 | 沿用现有小智形象制作 | 欢迎、思考、完成三个状态 |
| 空状态插画 | 同一套 SVG 或透明图片 | 空购物车、暂无订单、暂无活动 |
| 图标 | 延续现有图标体系，必要时补充 SVG | 导航、购物车、营养、文创 |
| 按钮、输入框、卡片 | HTML 和 CSS | 可点击、可切换状态的完整样板 |

首页插画可以先以电脑端约 1600×600、手机端约 750×900 作为构图草案，最终尺寸由页面实际位置决定。**手机端通常需要重新安排主体和留白，不能只把电脑图片缩小。**

#### 4.2 校园插画的制作要求

制作校园插画时，指令应具体到构图。例如：

> 参考所附校园建筑照片，制作简洁的校园生活插画。保留建筑可识别的轮廓，建筑安排在画面右侧，左侧约四成区域留给网页标题。沿用已经确认的色板和线条风格。图片中不生成校名、校徽、按钮或活动日期，这些由网页单独显示。

这么做之后，活动标题和日期可以随时修改，不用重新制作图片。

如果使用图像生成，先确认一张主视觉，再以它为参考扩展其他素材。每次要求“保持色板、线条粗细、人物比例一致”，整套素材才不容易出现风格漂移。

关于免费要求：**零新增费用可以优先采用已有的照片、代码绘制的 SVG 和 CSS。** 图像生成会消耗账户用量，不能保证无限免费，也没有必要为这个项目额外接入付费图片接口。

#### 4.3 制作可点击的组件展示页

让 Codex 做一个“组件展示页”，相当于整套皮肤的样品册。至少包含：

- 主按钮、次按钮、文字按钮、图标按钮。
- 默认、悬停、按下、键盘焦点、禁用、加载中状态。
- 输入框正常、聚焦、填写错误状态。
- 菜品卡片、食堂卡片、活动卡片。
- 导航选中态、标签、弹窗、购物车和提示消息。
- 手机和电脑两种宽度预览。

### 5. 主题配置如何制作

你负责说“按钮再柔和一点”“卡片边框不要太明显”；Codex 把这些判断转换成具体配置，不必手填。

```json
    "buttonRadius": "12px",
    "cardRadius": "20px"
  },
  "assets": {
    "heroDesktop": "cufe/hero-desktop.webp",
    "heroMobile": "cufe/hero-mobile.webp",
    "pattern": "cufe/pattern.svg"
  }
}
```

其中：

- `primary` 控制主要按钮和选中元素的品牌色。
- `onPrimary` 控制按钮上的文字颜色，避免更换主色后文字看不清。
- `shape` 控制按钮与卡片圆角。
- `assets` 指向实际制作好的校园素材。
- `version` 帮助网站识别主题已更新。

实际交付还应包含按下、禁用、焦点等状态，以及缺少素材时的默认处理。配置使用受控字段，每所学校主要填写颜色和素材即可。

现有的 `--zx-primary` 等 CSS 变量可以继续利用，Codex 负责把配置转换成这些变量。

### 6. 如何给出有效的设计反馈

给反馈时，描述 **“位置＋变化＋保留内容”**。

这一点非常影响最终质量。与其只说“再高级一点”，更有效的是：

> 保留当前布局和蓝白配色。首页插画缩小一些，让食堂状态在手机第一屏可见；按钮降低圆角，保留当前高度；页面背景纹样再淡一些。其他组件暂时不动。

或者：

> 采用第二版小智的表情，但保留第一版的头身比例、线条和颜色。只调整校园配饰，不重新设计整个形象。

每轮集中调整一类问题：先布局，再配色，再组件细节。确认过的设计规则应更新进同一份规范，避免下一轮又变回去。

### 7. 第三阶段：将已确认的设计接入真实页面

组件展示页通过后，先接入视觉，再处理账号绑定，便于判断问题来自样式还是登录流程。

首轮视觉接入应覆盖首页、点餐、营养师、文创、订单、个人中心、登录弹窗及购物车。不能只把首页做漂亮，其他页面仍保留旧颜色。

#### 可复制指令三：视觉接入与验证

> 我已确认当前高校主题的素材和组件展示页，现在授权将这套视觉接入“智饷”C 端。
>
> 先记录当前工作区基线，保留已有修改，列出本次涉及的文件，再实施以下内容：
>
> 1. 复用现有主题机制，接入已经验收的配置和素材。
> 2. 覆盖首页、点餐、营养师、文创、订单、个人中心、登录弹窗和购物车。
> 3. 将需要跟随主题的硬编码样式统一起来。
> 4. 高校视觉主题不得改变菜品排序、营养推荐、订单金额和登录权限。
> 5. 保留默认主题，主题或图片加载失败时仍能正常使用页面。
> 6. 检查手机与电脑布局、按钮各状态、文字对比度，以及主要操作是否被遮挡。
> 7. 提供修改清单、实际验证结果、预览入口和明确的回退方法。
>
> 本阶段只授权视觉接入，不修改数据库、不接入学校身份认证、不自动发布线上网站。
>
> 完成视觉验收后，再向我提交“学校绑定后自动换肤”的接口与数据变更方案。

后续自动换肤的部分，再单独要求 Codex 实现：

```text
学校与主题关联
   ↓
登录返回学校
   ↓
应用主题
   ↓
按账号缓存
   ↓
刷新恢复
   ↓
退出或换账号时正确重置
```

按此前检查，线上接口仍指向本机地址。因此，组件预览和视觉接入可以先完成；真正的跨设备登录绑定，还需要可公网访问的账号服务。

### 8. 验收重点

1. 第一眼能否识别校园特色，同时能快速找到点餐入口。
2. 小屏手机上，标题、插画、按钮是否挤在一起。
3. 按钮能否明确区分可点击、已选中、加载中和不可用。
4. 切换主题后，弹窗、购物车、输入框是否一起变化。
5. 主题是否改变了不该改变的业务结果。
6. 图片加载失败时，文字和操作是否仍然可用。

让 Codex 同时做对比度检查：普通文字通常至少达到 4.5∶1；触控按钮建议保持约 44 像素的操作区域；有动画时提供减少动态效果的适配。

最终应拿到的是 **设计规范、素材包、主题配置、组件展示页、已接入页面和验收记录**。有了这些，第二所学校就能沿用组件与流程，集中更换校园资料、配色和素材。
